# Пропозиція щодо використання продукційної моделі бази знань

## 1. Теоретичний опис продукційної моделі бази знань

Продукційна модель імітує процес мислення експерта, що розв'язує задачу за допомогою набору правил "ЯКЩО (умова), ТО (дія)". Вона складається з трьох компонентів:

1.  **База даних фактів (Робоча пам'ять):** Набір фактів, що описують поточну ситуацію (напр., початкові дані про гру/вправу). Поповнюється новими фактами в процесі роботи.
2.  **База правил (Довготривала пам'ять):** Набір продукційних правил у форматі `IF <умова> THEN <висновок/дія>`.
3.  **Механізм виведення (Інтерпретатор):** "Мозок" системи, що циклічно зіставляє факти з правилами і застосовує їх (процес прямого логічного виведення).

#### Критерій зупинки (Мета виведення)

1. Формальною метою процесу виведення є **заповнення всіх полів зі значенням `null`** в об'єкті(ах) поточної Робочої пам'яті. 
2. Процес зупиняється, коли або всі поля заповнені, або жодне з правил у Базі правил більше не може бути застосоване до наявного набору фактів.

#### Стратегія вирішення конфліктів
Для забезпечення передбачуваності та стабільності системи пропонується наступна комбінована стратегія:
1.  **Пріоритет правила:** Кожне правило має числовий пріоритет. Механізм виведення завжди обирає для виконання правило з найвищим пріоритетом серед усіх правил, що спрацювали.
2.  **Заборона перезапису:** Правило може бути застосоване для визначення певного атрибута **лише в тому випадку, якщо поточне значення цього атрибута є `null`**. Це гарантує, що перший успішний висновок, зроблений правилом з найвищим пріоритетом, є остаточним.

## 2. Загальні алгоритми використання продукційної моделі

#### Алгоритм для ALCD = 0.50 (Контекстуальна логіка)
Правила цього рівня описують зв'язки **між різними атрибутами однієї й тієї ж активності**. Вони використовують факти, отримані з тексту, для виведення інших, більш абстрактних фактів про цю ж активність.

#### Алгоритм для ALCD = 0.25 (Експертна оцінка)
Правила цього рівня спираються на **апріорні знання експерта про систему або методику**. Вони пов'язують простий ідентифікатор (напр., назву системи) з глибоким експертним знанням, яке неможливо вивести з опису самого об'єкта.

## 3. Структура Бази Даних Фактів

Нижче наведено JSON Schema, що валідує структуру об'єктів-фактів.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "База даних фактів",
  "description": "Схема для валідації об'єктів-фактів про комп'ютерні ігри або фізичні вправи в базі даних фактів.",
  "type": "object",
  "properties": {
    "fact_id": { "type": "string", "description": "Унікальний ідентифікатор факту" },
    "fact_type": { "type": "string", "enum": ["game", "exercise"], 
            "description": "Тип факту: game - комп'ютерна гра, exercise - фізична вправа" },
    "fact_name": { "type": "string", "description": "Назва факту" },
    "fact_description": { "type": ["string", "null"], "description": "Текстовий опис сценарію гри або фізичної вправи" },
    "primary_goal": { "type": ["string", "null"], "description": "Основна мета" },
    "primary_goal_source": { "type": ["string", "null"], "description": "Джерело даних для основної мети" },
    "body_position": { "type": ["string", "null"], "description": "Положення тіла" },
    "body_position_source": { "type": ["string", "null"], "description": "Джерело даних для положення тіла" },
    "body_area": { "type": ["string", "null"], "description": "Область тіла" },
    "body_area_source": { "type": ["string", "null"], "description": "Джерело даних для області тіла" },
    "movement_dynamics": { "type": ["string", "null"], "description": "Динаміка рухів" },
    "movement_dynamics_source": { "type": ["string", "null"], "description": "Джерело даних для динаміки рухів" },
    "board_type": { "type": ["string", "null"], "description": "Тип дошки" },
    "board_type_source": { "type": ["string", "null"], "description": "Джерело даних для типу дошки" },
    "application_sphere": { "type": ["string", "null"], "description": "Сфера застосування" },
    "application_sphere_source": { "type": ["string", "null"], "description": "Джерело даних для сфери застосування" },
    "difficulty": { "type": ["string", "null"], "description": "Рівень складності" },
    "difficulty_source": { "type": ["string", "null"], "description": "Джерело даних для рівня складності" },
    "additional_devices": { "type": ["array", "null"], "items": { "type": "string" }, "description": "Додаткові пристрої" },
    "additional_devices_source": { "type": ["string", "null"], "description": "Джерело даних для додаткових пристроїв" }
  },
  "required": ["fact_id", "fact_type", "fact_name"],
  "allOf": [
    {
      "if": { "properties": { "fact_type": { "const": "game" } } },
      "then": {
        "properties": {
          "game_system": { "type": "string", "description": "Назва ігрової системи, наприклад, PlankPad" },
          "gameplay_bricks": {
            "type": "array",
            "items": { "type": "string" },
            "description": "Типи GamePlay цеглинок"
          }
        },
        "required": ["game_system"]
      }
    },
    {
      "if": { "properties": { "fact_type": { "const": "exercise" } } },
      "then": {
        "properties": {
          "technique": { "type": "string", "description": "Методичні рекомендації із описом фізичних вправ, наприклад, CoolBoard" }
        },
        "required": ["technique"]
      }
    }
  ]
}
```

**Пояснюваність висновків:** ключовою вимогою до системи є її здатність пояснювати свої висновки (англ. *explainability*). Для цього кожне поле з даними супроводжується допоміжним полем `*_source`, яке фіксує джерело походження факту. Це дозволяє відповісти не лише на питання "**Що** система знає?", але й на питання "**Звідки** вона це знає?".

Існує два основні типи джерел:
*   `"initial_text"`: факт отримано безпосередньо з початкових вхідних даних, наприклад, з текстового опису сценарію гри або фізичної вправи.
*   `"rule:R_..."`: факт був логічно виведений системою за допомогою застосування конкретного правила з бази правил.

Такий підхід є критично важливим для довіри до системи, її налагодження та подальшого аналізу бази знань.

*Примітка: Наведені нижче приклади демонструють **кінцевий стан** об'єктів у Базі даних фактів, після того, як механізм виведення застосував усі релевантні правила і заповнив початково порожні (`null`) поля.*

## 4. Структура Бази Даних Правил

Нижче наведено JSON Schema, що валідує структуру об'єктів-правил.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Правило",
  "description": "Схема для валідації правил в базі даних правил",
  "type": "object",
  "properties": {
    "rule_id": { "type": "string", "description": "Унікальний ідентифікатор правила" },
    "rule_name": { "type": "string", "description": "Назва правила" },
    "rule_type": { "type": "string", "enum": ["contextual", "expert"], "description": "Тип правила. 'contextual' правила (ALCD=0.50) виводять значення з контексту всередині факту (наприклад, з текстового опису). 'expert' правила (ALCD=0.25) спираються на зовнішні, апріорні знання (наприклад, про конкретну ігрову систему)." },
    "priority": { "type": "integer", "description": "Пріоритет виконання правила" },
    "if": { "$ref": "#/$defs/conditionGroup", "description": "Блок умов 'ЯКЩО'." },
    "then": {
      "type": "array",
      "description": "Блок дій 'ТОДІ', який виконуються за істиності умови",
      "items": { "$ref": "#/$defs/action" }
    }
  },
  "required": ["rule_id", "rule_name", "rule_type", "priority", "if", "then"],
  "$defs": {
    "conditionGroup": {
      "type": "object",
      "description": "Група умов, об'єднаних логічним оператором. Це дозволяє створювати складні логічні вирази.",
      "properties": {
        "operator": { "type": "string", "enum": ["AND", "OR"], "description": "Логічний оператор, що об'єднує умови в групі ('І' або 'АБО')." },
        "conditions": {
          "type": "array",
          "description": "Масив, що містить одну або декілька умов. Кожна умова може бути простою (`simpleCondition`) або вкладеною групою (`conditionGroup`), що дозволяє рекурсивно будувати логіку.",
          "items": {
            "oneOf": [
              { "$ref": "#/$defs/simpleCondition" },
              { "$ref": "#/$defs/conditionGroup" }
            ]
          }
        }
      },
      "required": ["operator", "conditions"]
    },
    "simpleCondition": {
      "type": "object",
      "description": "Проста атомарна умова для перевірки одного факту. Це базовий 'будівельний блок' логіки.",
      "properties": {
        "criterion": { "type": "string", "description": "Назва факта-критерію з бази даних фактів, який потрібно перевірити (наприклад, 'body_position')" },
        "operator": { "type": "string", "enum": ["equals", "is_null", "contains"], "description": "Оператор для порівняння значення факта-критерію" },
        "value": { "type": "string", "description": "Значення, з яким порівнюється критерій. Не використовується для оператора 'is_null'" }
      },
      "required": ["criterion", "operator"]
    },
    "setValue": {
      "type": "object",
      "description": "Дія, що виконується, якщо умова правила (блок 'if') є істинною. Зазвичай це встановлення нового значення для факта-критерію.",
      "properties": {
        "criterion": { "type": "string", "description": "Назва факта-критерію для встановлення значення" },
        "value": { "type": "string", "description": "Нове значення факта-критерію" }
      },
      "required": ["criterion", "value"]
    }
  }
}
```

  * Для `contextual` правил:
       * Опис: У таких правилах опис акцентує увагу на взаємозв'язках між різними атрибутами в рамках одного об'єкта-факту або на аналізі безпосередньо fact_description (текстового опису). Він пояснює, як висновок
         робиться шляхом вивчення логічних залежностей або ключових слів, що містяться в самому факті.
       * Прикладні фрази: "Якщо опис містить...", "Якщо положення тіла є...", "Виводиться з *характеру руху*...", "Аналізуючи *назву*...", "Зв'язок всередині моделі..."
       * Приклад з `Knowleadge_Proposition.md` (R_PhysFocus_01):
          > "Це правило є контекстуальним і визначає клас за критерієм 'Область тіла'. Якщо з опису відомо, що вправа виконується в положенні 'Планка', і при цьому область тіла ще не визначена, тоді 'Опис тіла' =
  'Кор'." (Тут "опис" вказує на внутрішні атрибути факту.)

   * Для `expert` правил:
       * Опис: У цих правилах опис чітко вказує на залежність від зовнішньої інформації або апріорних знань. Він пояснює, як висновок робиться шляхом зіставлення поточного факту з ширшою, заздалегідь визначеною   
         базою знань або метаданими, що не містяться в прямому описі факту.
       * Прикладні фрази: "Спирається на *знання про систему*...", "Вимагає *зовнішніх знань*...", "Якщо система є...", "Визначення на основі *методики*...", "Це апріорне знання..."
       * Приклад з `Knowleadge_Proposition.md` (R_BoardType_01):
          > "Це правило є експертним, оскільки воно спирається на знання, які неможливо вивести безпосередньо з опису гри. Воно стверджує, що якщо гра належить до системи 'Wii Fit', то для неї використовується    
  специфічний тип обладнання – 'Pressure-sensor board'." (Тут виділено залежність від зовнішнього знання про систему "Wii Fit".)

## 5. Опис Бази Даних Правил для критеріїв

*Примітка: Всі наведені нижче правила діють за політикою "заборони перезапису", що реалізовано через умову `"operator": "is_null"` для цільового критерію. Варто зазначити, що згідно зі схемою, кожна умова, навіть якщо вона одна, є елементом `simpleCondition`, що міститься всередині `conditionGroup`.*

---
#### **Критерій: Положення тіла** (ALCD = 0.50)
*   **Опис правила:** Це правило демонструє найпростіший випадок. Воно перевіряє лише одну умову: якщо в назві гри чи вправи зустрічається слово "планка" (у будь-якому регістрі), і `body_position` ще не визначено, то система встановлює `body_position` рівним "Планка". Це приклад того, як одна проста умова (`simpleCondition`) використовується всередині `conditionGroup`.
*   **Правило:**
    ```json
    {
      "rule_id": "R_BodyPos_01",
      "rule_name": "Визначення_положення_тіла_за_назвою",
      "rule_type": "contextual",
      "priority": 110,
      "if": {
        "operator": "AND",
        "conditions": [
          {
            "criterion": "fact_name",
            "operator": "contains",
            "value": "планка"
          },
          {
            "criterion": "body_position",
            "operator": "is_null"
          }
        ]
      },
      "then": [
        {
          "criterion": "body_position",
          "value": "Планка"
        }
      ]
    }
    ```

---
#### **Критерій: Область тіла** (ALCD = 0.50)
*   **Опис правила:** Це правило є контекстуальним і визначає клас за критерієм "Область тіла". 
Якщо з опису відомо, що вправа виконується в положенні "Планка", і при цьому область тіла ще не визначена, тоді "Опис тіла" = "Кор".
*   **Правило (приклад у новому форматі):**
    ```json
    {
      "rule_id": "R_PhysFocus_01",
      "rule_name": "Визначення_області_тіла_для_планки",
      "rule_type": "contextual",
      "priority": 100,
      "if": {
        "operator": "AND",
        "conditions": [
          {"criterion": "body_position", "operator": "equals", "value": "Планка"},
          {"criterion": "body_area", "operator": "is_null"}
        ]
      },
      "then": [{"criterion": "body_area", "value": "Кор"}]
    }
    ```

---
#### **Критерій: Динаміка рухів** (ALCD = 0.50 / 0.75)
*   **Опис правила:** Це правило є контекстуальним і визначає динаміку рухів на основі ключових слів у текстовому описі. Якщо опис містить слово "утримуйте", і `movement_dynamics` ще не визначено, система встановлює `movement_dynamics` як "Статичне утримання".
*   **Правило:**
    ```json
    {
      "rule_id": "R_MoveDyn_01",
      "rule_name": "Визначення_динаміки_рухів_за_описом",
      "rule_type": "contextual",
      "priority": 100,
      "if": {
        "operator": "AND",
        "conditions": [
          {
            "criterion": "fact_description",
            "operator": "contains",
            "value": "утримуйте"
          },
          {
            "criterion": "movement_dynamics",
            "operator": "is_null"
          }
        ]
      },
      "then": [
        {
          "criterion": "movement_dynamics",
          "value": "Статичне утримання"
        }
      ]
    }
    ```
