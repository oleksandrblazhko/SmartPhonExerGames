# Модель GamePlay-Bricks 3.0 для опису механік комп'ютерних ігор

## 1) Механіка "Досягнення" (Achieve), тип "Ціль" (Goal).

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Механіка пропонує користувачеві підтримувати один або декілька елементів у певному місці або стані рівноваги. 
Наприклад, у грі "Понг" користувач не повинен дозволити м'ячу вийти за межі поля. 
Механіка спонукає користувача розташувати один або декілька елементів у ключових місцях або конфігураціях. 
Наприклад, у грі в пасьянс гравець повинен зуміти розмістити єдину фігуру, що залишилася, в центрі дошки в кінці гри. 
Механіка також спонукає користувача блокувати суперника або визначений елемент. Наприклад, поставити мат королівській фігурі в шахах.

### Текстове визначення моделі GamePlay-Bricks 3.0

Механіка відповідає на питання типу "Якщо...тоді...", яке передбачає зміну стану. 
Це перекладається як пошук збігу між змінними заданого екземпляра та значеннями змінних в іншому екземплярі або списку еталонних значень.
Якщо збіг знайдено, механіка повертає "true" та може діяти як тригер для локальної або глобальної цілі.
Примітка: Avoid є протилежністю механіка Achieve.

### Формалізоване текстове визначення

Припустимо Inst = Instance(1)
Припустимо Inst2 = Instance(2)
Припустимо V = {1 ; … ; v }
Припустимо R = {1 ; … ; r }

Inst — поточний екземпляр об'єкту;
Inst2 — другий екземпляр об'єкту;

V — множина змінних стану екземпляру об'єкту Inst;
v — кількість змінних;

R — множина цільових значень;
r — кількість результатів;

Враховуючи, що v = r:

якщо (V(Inst) = R або V(Inst) = V(Inst2)), тоді Achieve = 1

### Datalog-опис

achieve(I) :-
    state(I, S),
    target(S).

achieve(I) :-
    state(I, S),
    state(I2, S),
    I != I2.

### Семантика правил Datalog-опису

1) Правило еталонної відповідності (Збіг із цільовим станом)
- Логічна семантика: Екземпляр ігрового об'єкта I вважається таким, що виконав умову механіки, якщо його поточний аналізований стан S ідентичний константній цілі або списку еталонних значень target(S).
- Ігрове (інтенційне) значення:
    - Перевірка умов перемоги/прогресу: Гравець або об'єкт досягли необхідної точки (наприклад, здоров'я боса S = 0, кількість зібраних монет S = 100).
    - Конфігураційне зведення: Об'єкт переведено у правильний стан з обмеженої множини валідних станів (наприклад, ключ повернуто у замку під правильним кутом, важіль переведено в положення "On").
    - Валідація еталону: Перевірка того, що дія користувача точно відтворює заздалегідь створений розробником паттерн (наприклад, правильний порядок символів у квесті-головоломці).
2) Правило реляційної відповідності (Збіг між об'єктами)
- Логічна семантика: Екземпляр I виконує умову механіки, якщо у поточному кадрі/системі існує інший екземпляр I2 (де унікальні ідентифікатори не збігаються: I != I2), який володіє точно таким самим значенням стану S.
- Ігрове (інтенційне) значення:
    - Просторова колізія (Зіткнення/Контакт): Якщо стан S репрезентує просторові координати (або ігровий сектор), правило фіксує перетин двох об'єктів. Це база для підбору предметів (гравець і аптечка в одній точці), входу в тригерну зону або наступання на пастку.
    - Механіка блокування або перехоплення: Опоненти опиняються в однакових умовах, що інтерпретується як обмеження дій (наприклад, взяття фігури в полон у настільних іграх, блокування руху супротивника в шахах).
    - Синхронізація станів: Визначення моментів, коли два незалежні об'єкти зрівнялися за певним показником (наприклад, "наздогнати лідера за кількістю очок", "зрівняти рахунок у матчі").

## 2) Механіка "Уникнення" (Avoid), тип "Ціль" (Goal).

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Цей елемент цільового типу спонукає користувача уникати елементів/ перешкод/ ворогів/ супротивників. 
У гоночній грі, такій як Need for Speed, гравець повинен уникати зіткнення з перешкодами своїм транспортним засобом.

### Текстове визначення моделі GamePlay-Bricks 3.0

Механіка перевіряє, чи набір змінних у заданому екземплярі, 
що беруть участь у перевірці локального або глобального збою гри, відрізняється від значень змінних іншого екземпляра або від списку еталонних значень. 
Якщо так, механіка вказує на те, що ціль, яка не мала бути досягнута, досягнута. 
Примітка: Achieve є протилежністю механіки Avoid.

### Формалізоване текстове визначення

Припустимо Inst = Instance (1)
Припустимо Inst2 = Instance (2)
Припустимо V = {1 ; … ; v }
Припустимо R = {1 ; … ; r }

де Inst — еталонний екземпляр ігрового об’єкта, який береться до розгляду;
де Inst2 — другий екземпляр ігрового об’єкта;
де V — множина змінних, які мають бути досягнуті для екземпляра,
а v — кількість змінних;
де R — множина очікуваних результатів для екземпляра Inst,
а r — кількість результатів;

враховуючи, що кількість змінних v дорівнює кількості результатів r:
Поки (Inst.V != R або Inst.V != Inst2.R), тоді Avoid = 1

(Поки для кожного екземпляра множина елементів V відповідає множині елементів R
(R може бути включена або не включена до другого екземпляра Inst2),
тоді Avoid повертає значення 1 (істина).)

### Datalog-опис

% [Правило 1]: Фіксація критичного збігу з небезпечним еталоном (провал уникнення)
failed_avoid_target(I) :-
    state(I, S),
    target(S).

% [Правило 2]: Фіксація критичного зіткнення між двома об'єктами (провал уникнення)
failed_avoid_collision(I) :-
    state(I, S),
    state(I2, S),
    I != I2.

% [Правило 3]: Перевірка успішного уникнення еталонних загроз
avoid_target(I) :-
    state(I, _),
    not failed_avoid_target(I).

% [Правило 4]: Перевірка успішного уникнення динамічних перешкод/ворогів
avoid_collision(I) :-
    state(I, _),
    not failed_avoid_collision(I).

% [Правило 5]: Загальний стан механіки Avoid (Ціль досягнута, якщо немає жодних провалів)
avoid(I) :-
    avoid_target(I),
    avoid_collision(I).

### Семантика правил Datalog-опису:
1) Фіксація критичного збігу з небезпечним еталоном:
- Правило визначає допоміжний предикат failed_avoid_target(I), який стає істинним, якщо поточний стан об'єкта I збігається із заздалегідь визначеним тригером небезпеки або зоною поразки target(S).
- Семантично це означає:
    - Фіксацію порушення правил або виходу за межі дозволеного стану ($V(Inst) = R$).
    - В ігровому контексті: гравець наступив на лаву, закінчився таймер гри (час досяг 0), або рівень палива впав до критичного мінімуму.Це правило є "детектором помилки" гравця щодо статичного середовища гри.
2) Фіксація критичного зіткнення між двома об'єктами:
- Правило визначає допоміжний предикат failed_avoid_collision(I), який стає істинним, 
якщо у світі існує інший об'єкт I2 (з іншим ID), чий стан (наприклад, координати) повністю збігається зі станом об'єкта I.
- Семантично це означає:
    - Фіксацію просторового або логічного накладання двох динамічних сутностей (V(Inst) = V(Inst2).
    - В ігровому контексті: фіксація фізичного удару (машина врізалася в іншу машину, персонаж зіткнувся з ворогом, снаряд влучив у текстуру гравця).
    - Це правило є "детектором колізії" між рухомими або незалежними об'єктами гри.    
3) Перевірка успішного уникнення еталонних загроз:
- Правило оголошує стан avoid_target(I) істинним для об'єкта I, якщо об'єкт існує у грі (має хоча б якийсь стан _), і при цьому оператор безпечного заперечення not підтверджує, що інваріант правила [Правило 1] не виконався.
- Семантично це означає:
    - Підтвердження того, що об'єкт успішно ігнорує статичні пастки або обмеження системи.
    - В ігровому контексті: гравець утримує персонажа в межах безпечної ігрової зони (наприклад, не вилітає за межі екрана у Flappy Bird).
4) Перевірка успішного уникнення динамічних перешкод/ворогів:
- Правило оголошує стан avoid_collision(I) істинним, якщо за допомогою оператора not доведено, 
що об'єкт I не перебуває в стані зіткнення з жодним іншим об'єктом світу з [Правило 2].
- Семантично це означає:
    - Декларацію чистого простору навколо об'єкта. Квантор загальності гарантує: для всіх існуючих I2 немає перетину за координатами.
    - В ігровому контексті: успішне маневрування, ухилення від ворожих атак, збереження безпечної дистанції.
5) Загальний стан механіки Avoid:
- Головне правило механіки, яке повертає кінцеве значення Avoid = 1 (істина) для екземпляра I тоді й тільки тоді, коли одночасно виконуються умови [Правило 3] та [Правило 4].
- Семантично це означає:
    - Комплексну валідацію цілі типу "Уникнення": механіка сигналізує системі, що гравець діє успішно, не порушує правила і не наражається на небезпеку з жодного боку.
    - Поки avoid(I) повертає істину, локальні чи глобальні тригери збою (Game Over, втрата життя) залишаються неактивними, і ігровий процес триває далі.

### Текстове визначення моделі GamePlay-Bricks 3.0

Механіка пов'язана з механіками типу Ціль (Goal) або Засоби (Means). 
Якщо пов'язана механіка запитує це, Create генерує потрібні елементи (Екземпляри, змінні та дані).
Примітка: Destroy є протилежністю цеглинці Create.

### Формалізоване текстове визначення

Припустимо BG <=> BO або BM або M  
Припустимо Inst = Instance (n)  
Припустимо V = {1 ; … ; v }  
Припустимо D = {1 ; … ; d }  

де BG — механіка Gameplay типу "Ціль" (BO) або типу "Засіб" (BM)  
або типу Мета-механіка (M), пов’язана з механікою Create;

де Inst — множина з n екземплярів, які потрібно створити;  
де V — множина змінних, пов’язаних з кожним екземпляром n,  
а v — кількість змінних;  
де D — множина даних, які потрібно присвоїти кожній змінній з V,  
а d — кількість даних;

враховуючи, що кількість змінних v дорівнює кількості результатів d:

Якщо (BG == 1) тоді {
Створити Inst  
Створити Inst. V  
V = D  
}

з умовами n > 0, v > 0, d > 0.

(Якщо BG повертає 1 (істина), 
тоді створюється n екземплярів і v змінних, пов’язаних з кожним екземпляром, 
із присвоєнням даних із множини D.)

### Datalog-опис

% 1. Перевірка активації пов'язаної механіки (BG)
bg_active(MechanicID) :- goal_mechanic(MechanicID, active).
bg_active(MechanicID) :- means_mechanic(MechanicID, active).
bg_active(MechanicID) :- meta_mechanic(MechanicID, active).

% 2. Генерація нового екземпляра об'єкта при активації BG
create_instance(NewInstID, Type) :-
    bg_active(MechanicID),
    trigger_create(MechanicID, Type, NewInstID).

% 3. Присвоєння початкових значень (даних D) змінним (V) створеного екземпляра
instance_variable_state(NewInstID, Variable, DataValue) :-
    create_instance(NewInstID, Type),
    default_blueprint(Type, Variable, DataValue).

### Семантика правил Datalog-опису:
1) Правило делегування/активації тригера (bg_active)
- Логічна семантика: Запит на створення не може виникнути ізольовано. 
Це правило визначає контекст побудови: сукупність умов істинності ($BG == 1$) транслює активність від механік вищого рівня (Цілей, Засобів або Мета-правил) 
до виконавчого механізму створення.
- Ігрове (інтенційне) значення:
    - Умовний дозвіл на генерацію: Створення об'єкта стає легітимним лише тоді, коли гравець задіяв потрібний інструмент (натиснув кнопку "Побудувати хатину" — механіка Means) або виконав квест (відкрився портал — механіка Goal).
    - Абстракція джерела події: Системі "все одно", що саме викликало створення (скрипт рівня чи дія гравця), головне — наявність факту активації керуючої структури.
2) Правило матеріалізації екземпляра (create_instance)
- Логічна семантика: За умови активності тригера bg_active, система декларує появу нового унікального ідентифікатора об'єкта NewInstID, 
який належить до певного класу або типу Type. Це крок, який реалізує математичну умову $Inst = Instance(n)$ (де $n > 0$).
- Ігрове (інтенційне) значення:
    - Спавн (Spawn): Фізичне або логічне народження сутності в грі. Наприклад, випуск кулі зі зброї, поява нової хвилі ворогів, генерація процедурного всесвіту.
    - Інтенціальне виділення пам'яті: Створення порожньої сутності-"пакета", яка вже існує в структурі логіки гри, але ще не має індивідуальних параметрів.
3) Правило ініціалізації та наповнення даними (instance_variable_state)
- Логічна семантика: Для кожного новоствореного NewInstID його внутрішні змінні Variable (множина $V$) автоматично пов'язуються зі значеннями DataValue (множина даних $D$). Проекція відбувається на основі шаблону проектування (blueprint) конкретного типу об'єкта. Це забезпечує тотожність $v = d$.
- Ігрове (інтенційне) значення:
    - Налаштування початкових характеристик (Конфігурація): Створений об'єкт отримує свої індивідуальні властивості (наприклад, новий юніт отримує здоров'я = 100, 
    швидкість = 5, фракція = союзник). Без цього правила об'єкт залишався б абстрактним індексом.
    - Розміщення у світі: Присвоєння стартових просторових координат (змінні X, Y, Z отримують значення точки спавну).
    - Диференціація об'єктів: Завдяки шаблонам, механіка розуміє різницю між створенням "Орка-воїна" та "Орка-мага", автоматично наповнюючи їхні змінні різними пулами даних $D$.

## 4) Механіка "Руйнування" (Destroy), тип "Результати" (Outcomes)

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Механіку можна знайти в іграх, де потрібно знищувати елементи або ворогів. 
Наприклад, Space Invaders (Taito, 1978) запрошує гравця знищити всі ворожі кораблі, щоб виграти рівень. 
Механіка також символізує ідею збирання або захоплення предметів: їх можна фіксувати, переміщувати або навіть з'являти періодично. 
Таку цеглинку можна знайти, наприклад, у грі Pac-Man, де всі кульки повинні бути зібрані гравцем, щоб перейти на наступний рівень.
Інший приклад - пригодницькі ігри, які вимагають збирання предметів у навколишньому середовищі, щоб розмістити їх у зоні.

### Текстове визначення моделі GamePlay-Bricks 3.0

Механіка пов'язана з механіками типу Ціль (Goal) або Засоби (Means). 
Якщо пов'язана Механіка цього вимагає, Destroy видаляє потрібні елементи (екземпляри, змінні та дані).
Примітка: Create є протилежністю цеглинці Destroy.

### Формальне текстове визначення 

Припустимо BG <=> BO або BM або M  
Припустимо Inst = Instance (n)  
Припустимо V = {1 ; … ; v }  

де BG — механіка Gameplay типу Goal-типу (BO) і/або Means-типу (BM)  
або комбінація механік (M), пов’язана з механікою Destroy;

Припустимо Inst — множина з n екземплярів, які потрібно видалити;  
де V — множина змінних, пов’язаних з кожним екземпляром n,  
а v — кількість змінних;

враховуючи, що кількість змінних v дорівнює кількості результатів d:

Якщо (BG == 1) тоді {
Видалити Inst  
Видалити Inst.V  
}

з умовами n > 0 і v > 0.

(Якщо BG повертає 1 (істина), тоді видаляється n екземплярів і v змінних, пов’язаних з ними).

### Datalog-опис

% [Правило 1]: Визначення активності пов'язаної механіки-тригера (BG)
bg_destroy_trigger(MechanicID) :- goal_mechanic(MechanicID, active).
bg_destroy_trigger(MechanicID) :- means_mechanic(MechanicID, active).
bg_destroy_trigger(MechanicID) :- meta_mechanic(MechanicID, active).

% [Правило 2]: Генерація запиту на видалення екземпляра об'єкта (Inst)
request_destroy_instance(InstID) :-
    bg_destroy_trigger(MechanicID),
    target_for_destruction(MechanicID, InstID).

% [Правило 3]: Автоматичне маркування всіх змінних об'єкта на видалення (Inst.V)
request_destroy_variable(InstID, Variable) :-
    request_destroy_instance(InstID),
    state(InstID, Variable, _).

% [Правило 4]: Фільтрація стану світу (Логічне видалення об'єктів та їхніх змінних)
retained_instance_state(InstID, Variable, Value) :-
    state(InstID, Variable, Value),
    not request_destroy_instance(InstID).

### Семантика правил Datalog-опису:
1) Визначення активності пов'язаної механіки-тригера:
- Правило реалізує геймдизайнерську умову: BG iff BO or BM or M. Воно зводить різні типи керуючих механік (Цілі, Засоби чи Метамеханіки) до єдиного сигналу готовності bg_destroy_trigger.
- Семантично це означає:
    - Перевірку легітимності руйнування: об'єкт не може зникнути сам по собі; для цього має спрацювати ігровий тригер ($BG == 1$).
    - В ігровому контексті: гравець виконав умову (наприклад, наніс фінальний удар мечем — механіка Means), або було досягнуто глобальної цілі (гравець зібрав усі монети на рівні, і вони мають зникнути з екрана — механіка Goal).
2) Генерація запиту на видалення екземпляра об'єкта:
- Правило пов'язує активний тригер bg_destroy_trigger із конкретним ідентифікатором об'єкта InstID, який було обрано як ціль для знищення (target_for_destruction).Семантично це означає:Ініціацію процесу видалення (Видалити Inst): ідентифікація конкретного екземпляра $n$ із множини об'єктів, який підлягає анігіляції.В ігровому контексті: визначення того, яка саме стіна має вибухнути, який саме ворожий корабель у Space Invaders підбито, або яку саме точку/кульку Pac-Man щойно з'їв.Виконується умова $n > 0$, оскільки правило оперує існуючими унікальними сутностями.
3) — Автоматичне маркування всіх змінних об'єкта на видалення
- Правило каже: якщо екземпляр InstID надійшов на видалення, то всі його внутрішні змінні Variable (множина $V$), які наразі існують у предикаті state, також маркуються як такі, що підлягають знищенню.
- Семантично це означає:
    - Каскадне очищення даних (Видалити Inst.V): гарантію того, що разом із тілом об'єкта з пам'яті гри будуть стерті всі його характеристики.
    - В ігровому контексті: якщо ворог знищений, гра має забути його поточний рівень здоров'я, його швидкість, тип його зброї та поточні координати. Це запобігає появі "об'єктів-привидів" або витоку даних у логіці симуляції.
    - Забезпечує виконання умови $v > 0 (видаляються всі пов'язані з об'єктом змінні).
4) — Фільтрація стану світу (Логічне видалення)
- Це ядро деструктивної логіки в Datalog. Предикат retained_instance_state формує новий, чистий стан ігрового світу. До нього потрапляють лише ті об'єкти та змінні, для яких оператор безпечного заперечення not підтвердив відсутність запиту на руйнування з [Правила 2].
- Семантично це означає:
    - Формальний акт руйнування: об'єкти, які потрапили під дію механіки Destroy, просто перестають існувати для решти ігрового коду в наступному ігровому циклі (кадрі).
    - В ігровому контексті: куля зникла з екрана після влучання; Pac-Man з'їв кульку, і вона більше не рендериться і не враховується системою; підібраний квестовий предмет зник із землі та перейшов у стан "інвентарю" (інший екземпляр).
    - Повну зміну парадигми світу: система успішно перейшла у стан, де $Inst$ та $Inst.V$ більше не валідуються іншими аналітичними механіками (наприклад, механіка Avoid більше не буде фіксувати з ними колізій).

## 5) Механіка "Керування" (Manage), тип "Умови" (Conditions)

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Механіка пропонує користувачеві керувати ресурсами відповідно до конкретних цілей. 
Наприклад, кількість пального, необхідного для проїзду транспортного засобу якомога далі, 
або необхідність поповнення боєприпасів
у стрілялці. Або кількість військ у стратегії в реальному часі, такій як Warcraft, 
або сировина в економічному симуляторі тощо.

### Текстове визначення моделі GamePlay-Bricks 3.0

Механіка пов'язана з Механіками типу Засоби (Means).
Перевіряє наявність необхідних ресурсів. 
Якщо умова виконується, Механіка дозволяє запуск пов’язаної цеглинки типу Means, 
інакше — відмовляє у її виконанні.

### Формалізоване текстове визначення

Припустимо BG <=> BM
Припустимо V(BG) = {1 ; ... ; v } 
Припустимо R = {1 ; ... ; r }
де BG — GamePlay-механіка типу "Засіб" (BM), пов'язана з механікою Manage;
де V(BG) — множина доступних Ресурсів відносно механіки BG, а v — кількість змінних; 
де R — множина необхідних Ресурсів, а r — загальна кількість ресурсів, які потрібно перевірити;
Якщо (V(BG) >= R), тоді Manage = 1, інакше Manage = 0 
(Якщо кожна змінна з множини V(BG) має значення, що є більшим або дорівнює кожному з відповідних значень у множині R, 
тоді механіка Manage повертає значення 1 (Істина), інакше вона повертає 0 (Хибність).)

### Datalog-опис
% [Правило 1]: Порівняння окремої доступної змінної ресурсу V(BG) із необхідною нормою R
resource_variable_sufficient(BM_ID, ResourceVar) :-
    available_resource(BM_ID, ResourceVar, AvailableValue),
    required_resource(BM_ID, ResourceVar, RequiredValue),
    AvailableValue >= RequiredValue.

% [Правило 2]: Фіксація браку бодай одного ресурсу (Детекція умови Manage = 0)
gerer_failed(BM_ID) :-
    required_resource(BM_ID, ResourceVar, _),
    not resource_variable_sufficient(BM_ID, ResourceVar).

% [Правило 3]: Активація механіки Manage = 1 (Якщо жодна перевірка не провалена)
gerer_success(BM_ID) :-
    required_resource(BM_ID, _, _), % Валідація, що для BM взагалі існують вимоги до ресурсів
    not gerer_failed(BM_ID).

% [Правило 4]: Дозвіл на виконання механіки засобів
execute_brique_moyen(BM_ID) :-
    intent_to_act(BM_ID),
    gerer_success(BM_ID).

### Семантика правил Datalog-опису:
1) — Порівняння доступної змінної ресурсу з нормою
- Правило зіставляє поточне значення наявного ресурсу AvailableValue (елемент множини V(BG)) із потрібним значенням RequiredValue (елемент множини R) 
для конкретної механіки дій BM_ID.
- Семантично це означає:
    - Математичну перевірку локальної умови нерівності для кожної окремої змінної ресурсу.
    - В ігровому контексті: перевірку, чи поточна кількість палива >= вартості ходу, або чи поточна кількість золота >= вартості найму воїна.
2) — Фіксація браку бодай одного ресурсу (Умова Manage = 0)
- Правило використовує заперечення not. Предикат gerer_failed стає істинним, якщо в системі існує хоча б один необхідний для цієї дії ресурс ResourceVar, який не задовольнив умову [Правила 1] (тобто наявна кількість виявилася меншою за необхідну).
- Семантично це означає:
    - Логічний преривач (Short-circuit): якщо для побудови об'єкта потрібні 3 типи ресурсів (наприклад, дерево, залізо, золото), 
    а гравцеві бракує лише золота, правило миттєво фіксує загальний провал ресурсної перевірки для всієї механіки BM.
3) — Активація механіки (Якщо (V(BG) >= R), тоді Manage = 1):
- Правило оголошує успіх транзакції керування gerer_success, якщо за допомогою оператора not доведено, що предикат провалу [Правило 2] не згенерував жодного факту (тобто gerer_failed є хибним).
- Семантично це означає:
    - Реалізацію квантора загальності ( для всіх елементів): подвійне заперечення в Datalog гарантує, 
    що кожна змінна з множини V(BG) успішно пройшла перевірку на рівність або перевищення еталону з множини R (V(BG) >= R).
    - Механіка повертає істину (Manage = 1), виступаючи зеленим світлом для ігрової симуляції.
4) — Дозвіл на виконання механіки засобів:
- Правило пов'язує суб'єктивний намір гравця або системи виконати дію (intent_to_act) із позитивним вердиктом механіки керування з [Правила 3].
- Семантично це означає:
    - Контроль доступу (Guard Condition): блокування або дозвіл на зміну стану гри. 
    Тільки якщо Manage = 1, дія типу Means (BM) (наприклад, постріл, переміщення, заклинання) отримає фізичне виконання в ігровому движку.
    Якщо Manage = 0, правило не спрацює, і гра відмовить користувачеві у виконанні дії (наприклад, виведе повідомлення "Недостатньо ресурсів").

## 6) Механіка "Вибір" (Select), тип "Засоби" (Means).

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Механіка пропонує користувачеві вибрати елемент на екрані за допомогою будь-якого типу пристрою введення (клавіатури, геймпада тощо).
До програм, що містять цей елемент, належать, наприклад, пригодницькі ігри, 
в яких іноді доводиться вибирати параметри діалогу, вибирати предмет з інвентарю тощо.
Він також може включати ігри на спостереження, такі як ігри на знаходження відмінностей, 
де користувач повинен клацати на графічні елементи, які відрізняються від одного зображення до іншого, 
або навіть відтворювати певну послідовність одночасно або по черзі. 
Механіка також стосується можливості запускати певну функцію в грі: зміна зброї в FPS, вибір будівлі будівлі в SimCity тощо.

### Текстове визначення моделі GamePlay-Bricks 3.0

Зберігає в одній або кількох змінних принаймні одного заданого екземпляра отриманий вибір.

### Формалізоване текстове визначення

Припустимо Inst = Instance (n)  
Припустимо V(Inst) = {1 ; … ; v }  
Припустимо C = {1 ; … ; c }  

де Inst — множина цільових екземплярів;  
де n — кількість екземплярів;  
де V(Inst) — множина змінних v, пов’язаних зі значеннями вибору для Inst;  
де C — множина змінних c, пов’язаних із здійсненими виборами;

Якщо (Select == 1) тоді {
V(Inst) = Select (list, C)
}

де list — список елементів, серед яких необхідно здійснити вибір.

(Якщо вибір зафіксовано, тоді необхідно заповнити кожну змінну множини V(Inst) значеннями вибору C, здійсненими зі списку list.)

### Datalog-опис
% [Правило 1]: Валідація наявності елемента у доступному для вибору списку (list)
item_in_choice_list(ListName, ChoiceID) :-
    choice_list_content(ListName, ChoiceID).

% [Правило 2]: Фіксація акту вибору конкретного елемента користувачем (C)
player_selection_made(PlayerID, ListName, ChoiceID) :-
    player_input_select(PlayerID, ListName, ChoiceID),
    item_in_choice_list(ListName, ChoiceID).

% [Правило 3]: Оновлення змінних стану цільового екземпляра (V(Inst) = Select(list, C))
instance_selection_state(InstID, SelectionVariable, ChoiceID) :-
    target_instance_for_selection(InstID, SelectionVariable, ListName),
    player_selection_made(_, ListName, ChoiceID).

### Семантика правил Datalog-опису:
1) — Валідація наявності елемента у доступному списку:
- Правило перевіряє, чи належить певний варіант ChoiceID до офіційного ігрового списку ListName.
- Семантично це означає:
    - обмеження простору вибору (list): система гарантує, що гравець не може вибрати те, чого немає в поточному меню.
    - В ігровому контексті: перевірка, чи дійсно ця репліка є в діалоговому вікні квесту, чи є будівля в списку доступних для спорудження (SimCity), або чи є зброя в круговому меню вибору (FPS).
2) — Фіксація акту вибору (Select == 1):
- Правило поєднує фізичний або логічний сигнал натискання/введення від гравця (player_input_select) із підтвердженням валідності цього елемента з [Правила 1]. 
Результатом є генерація факту player_selection_made, що відповідає множині здійснених виборів C.
- Семантично це означає:
    - Реєстрацію події інтерфейсу: фіксацію моменту, коли абстрактна можливість вибору перетворюється на конкретне рішення гравця.
    - В ігровому контексті: клік мишкою по предмету в інвентарі, натискання гарячої клавіші зміни зброї або вибір гілки розвитку в дереві навичок.
3) — Оновлення змінних стану цільового екземпляра
- Це ядро механіки, яке виконує присвоєння V(Inst) = Select(list, C). 
Якщо вибір ChoiceID зафіксовано, правило записує це значення у відповідну змінну стану SelectionVariable цільового об'єкта InstID.
- Семантично це означає:
    - Мутацію/Трансформацію стану об'єкта (V(Inst) = C): збереження вибору в пам'яті гри для подальшого використання іншими механіками.
    - В ігровому контексті:
        - Змінна поточного екіпірування персонажа InstID змінює значення на "Дворучний меч";
        - Змінна активного діалогу з NPC-персонажем записує вибір агресивної відповіді, що змінить подальший сюжет;
        - Курсор будівництва отримує інструмент "Дорога", і наступний клік по карті запустить механіку Create для створення дорожнього полотна.
    - Виконуються умови n > 0 та v > 0, оскільки для кожного обраного об'єкта заповнюються його конкретні змінні вибору.

## 7) Механіка "Рух" (Move), тип "Засоби" (Means).

### Текстове визначення для старої моделі GamePlay-Bricks 2.0

Механіка зустрічається в іграх, де потрібно керувати/пілотувати об'єктом або персонажем. 
Наприклад, у гоночній грі, такій як Action Driving Game, гравцеві пропонується керувати автомобілем.

### Текстове визначення моделі GamePlay-Bricks 3.0

next_spatial_position(InstID, NewX, NewY, NewZ) :-
    movement_intent(InstID, dX, dY, dZ),
    current_state(InstID, x_coord, CurrentX),
    current_state(InstID, y_coord, CurrentY),
    current_state(InstID, z_coord, CurrentZ),
    NewX = CurrentX + dX,
    NewY = CurrentY + dY,
    NewZ = CurrentZ + dZ.

% [Правило 2]: Обчислення нових часових та кінематичних параметрів об'єкта (T, R)
next_kinematic_state(InstID, NewT, NewR) :-
    movement_intent(InstID, _, _, _), % Перевірка, що рух активний (DEPLACER == 1)
    current_state(InstID, time_stamp, CurrentT),
    current_state(InstID, rotation, CurrentR),
    movement_delta(InstID, dT, dR),
    NewT = CurrentT + dT,
    NewR = CurrentR + dR.

% [Правило 3]: Формування оновленого вектора стану екземпляра для наступного кадру гри
next_frame_state(InstID, Variable, NewValue) :-
    Variable = x_coord, next_spatial_position(InstID, NewValue, _, _);
    Variable = y_coord, next_spatial_position(InstID, _, NewValue, _);
    Variable = z_coord, next_spatial_position(InstID, _, _, NewValue).

next_frame_state(InstID, Variable, NewValue) :-
    Variable = time_stamp, next_kinematic_state(InstID, NewValue, _);
    Variable = rotation, next_kinematic_state(InstID, _, NewValue).
